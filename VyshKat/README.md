## Запуск

Нужен .NET SDK 8.

dotnet build
dotnet run --project src/VyshKat.App
dotnet run --project src/VyshKat.App -- мой_файл.csv
dotnet run --project src/VyshKat.App -- --no-demo
dotnet test

При запуске программа сначала показывает демонстрацию: принимает технику из файла `demo.csv` (лежит в `src/VyshKat.App`) и выводит все отчёты. После этого открывается меню, где можно работать вручную. Можно передать свой файл вместо `demo.csv` или отключить демонстрацию ключом `--no-demo`.
В меню есть пункт 7 — загрузить технику из файла. Если ввести что-то неправильно, программа переспросит. Дробные числа можно писать и через точку, и через запятую.

Формат файла: одна строка — один объект, поля через `;`. Первое поле — код вида, модель и состояние в процентах, потом поля, которые зависят от вида:
SC (самокат), BK (велосипед): простота для новичка;
ESC (электросамокат), EBK (электровелосипед): простота для новичка; расход кВт ч в сутки;
HLM (шлем): размер;
DCK (док-станция), CHG (зарядный шкаф): число слотов; расход кВт ч в сутки.
Пример: `ESC;ВышКат E-Lite;95;7;0.45`. Пустые строки и строки с `#` пропускаются. Ошибочная строка не ломает загрузку: программа пишет номер строки и причину и идёт дальше.

## Как устроено

Решение состоит из трёх проектов:
`VyshKat.Core` — модель и логика;
`VyshKat.App` — консольное меню и настройка DI;
`VyshKat.Tests` — тесты.

Всё, что стоит на балансе, наследуется от `Asset`. У любого такого объекта есть инвентарный номер, наименование и техническое состояние в процентах. Дальше два направления:
`Vehicle` — транспорт (самокат, велосипед, электросамокат, электровелосипед). Есть «простота для новичка» от 1 до 10.
`Equipment` — вещи (шлем, док-станция, зарядный шкаф).

Отдельно есть два интерфейса:
`IInventoriable` — у объекта есть инвентарный номер и наименование;
`IEnergyConsumer` — объект потребляет энергию (суточный расход в кВт·ч).

`IEnergyConsumer` реализуют только электросамокат, электровелосипед, док-станция и зарядный шкаф.

Приём в парк делает `FleetAcceptanceService`. Сначала он проверяет, что такого инвентарного номера ещё нет, потом отправляет объект на техосмотр (`IServiceCenter`) и только после этого ставит на баланс. Штатный `ServiceCenter` принимает объект, если его состояние не ниже 70%. Техосмотр проходят и вещи: шлем с трещиной тоже не нужен^_^.

Отчёты считает `FleetReportService`. Правило «для новичков» вынесено в `IBeginnerPolicy`. Сейчас это `SimplicityBeginnerPolicy`: простота должна быть не меньше 6.

Данные для демонстрации не зашиты в код: они лежат в `demo.csv` и читаются через `FileImporter`. Импорт из файла и ввод с клавиатуры используют одни и те же правила создания объектов (`AssetKind`), разница только в источнике ответов: при чтении файла `ConsolePrompter` не переспрашивает, а сообщает об ошибке. Бизнес-логика (`VyshKat.Core`) не знает, откуда пришли данные — с клавиатуры или из файла.

Инвентарные номера выдаёт `InventoryNumberGenerator` в формате `VK-ESC-0001`: префикс компании, код вида и порядковый номер внутри вида. Номер присваивается при оформлении приёмки. Если объект не прошёл техосмотр, номер второй раз не используется.

## SOLID

S. У каждого класса одна задача. `ServiceCenter` решает про техосмотр, `SimplicityBeginnerPolicy` — про новичков, `FleetAcceptanceService` отвечает за порядок приёмки, `FleetReportService` считает отчёты, а `ReportPrinter` печатает их в консоль. `ConsolePrompter` читает и проверяет ввод, `ConsoleMenu` только переключает пункты меню.

O. Отчёты работают через `IEnergyConsumer`, `Vehicle` и `Asset`, а не через конкретные классы. Новый вид транспорта попадает во все отчёты без правок отчётов. Меню приёмки строится из списка зарегистрированных видов (`AssetKind`), поэтому новый вид появляется в меню без изменения кода меню.

L. Любой наследник `Asset` можно передать в приёмку и в отчёты, и всё будет работать.

I. Интерфейсы маленькие: `IInventoriable`, `IEnergyConsumer`, `IServiceCenter`, `IBeginnerPolicy`. Шлем не будет иметь расход энергии, а зарядный шкаф — простоту для новичка.

D. `FleetAcceptanceService` зависит от `IServiceCenter` и `IFleetRepository`, а `FleetReportService` — от `IBeginnerPolicy` и `IFleetRepository`. Конкретные классы подставляются в одном месте, в `ServiceRegistration`. Поэтому в тестах техосмотр легко заменить, а хранение в памяти потом можно поменять на БД.

Не делал: интерфейсы для `FleetAcceptanceService`, `FleetReportService`, `InventoryNumberGenerator` и `ConsolePrompter`. У каждого из них одна реализация, и подменять их незачем. Так же не стал делать систему правил для техосмотра.

## DI

Используется `Microsoft.Extensions.DependencyInjection`. Все регистрации лежат в `ServiceRegistration.AddVyshKat`, а `Program.cs` только собирает контейнер, запускает демонстрацию и меню. Все сервисы зарегистрированы как Singleton: парк один на всё приложение.

Ввод и вывод тоже передаются через DI.

## Тесты

93 теста на xUnit, моки сделаны на Moq. Покрытие считается командой `dotnet test --collect:"XPlat Code Coverage"`.

Тесты:
`Core` — модель, техосмотр, правило для новичков, приёмка и отчёты;
`App` — сборка через DI-контейнер, подмена техосмотра, сценарии работы с меню и загрузка из файла.

## Ответы на вопросы

*какой принцип SOLID применён наиболее явно и где*

Инверсия зависимостей вокруг техосмотра. `FleetAcceptanceService` не знает, как именно проверяют технику: он получает `IServiceCenter` через конструктор и просто выполняет решение. Какая реализация будет использоваться, задаётся в `ServiceRegistration`. Из-за этого в тестах техосмотр заменяется на заглушку, а правила можно менять, не трогая приёмку.

*какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо*

Инверсия зависимостей применена не везде. `FleetAcceptanceService`, `FleetReportService`, `InventoryNumberGenerator` и `ConsolePrompter` внедряются как обычные классы, без интерфейсов. Вторая реализация у них не нужна, а интерфейс ради интерфейса был бы лишним.

Открытость/Закрытость: чтобы новый вид появился в меню, нужно дописать одну строку в `ServiceRegistration.AddAssetKinds`. Потому что `ServiceRegistration` и есть то место, которое знает про все реализации.

*что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада
запчастей (можете придумать свой вариант расширения программы)*

Новый вид транспорта, например моноколесо: добавляется класс `ElectricUnicycle : Vehicle, IEnergyConsumer` и одна строка регистрации. Приёмка, техосмотр, отчёты и тесты не меняются.

Сотрудники: их можно добавить отдельным классом со своим хранилищем. На баланс их поставить нельзя (`IFleetRepository.Add` принимает только `Asset`), и в отчёты они не попадут.

Склад запчастей: запчасти можно сделать отдельным классом, реализующим `IInventoriable`. Придётся поменять один метод, `GetInventory`, чтобы ведомость собиралась и из парка, и со склада. Остальное не затрагивается.

*какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется
зависимость*

Техосмотр:
`ServiceCenterTests` проверяет само правило: 69% не проходит, 70% проходит.
`FleetAcceptanceServiceTests` подменяет `IServiceCenter` через Moq и проверяет, что приёмка слушается решения техосмотра. Даже объект в идеальном состоянии не попадёт в парк, если техосмотр сказал «нет».
`DependencyInjectionTests` подменяет техосмотр прямо в DI-контейнере: в `TestApp.Build` вызывается `services.Replace(ServiceDescriptor.Singleton<IServiceCenter>(...))`. Подставляется либо свой класс `FakeServiceCenter`, либо мок из Moq.
`ConsoleMenuTests.FakeServiceCenter_InjectedIntoMenu_DecidesAcceptance` проверяет то же самое через меню.

Правило для новичков:
`SimplicityBeginnerPolicyTests` проверяет границу: 5 нельзя, 6 можно.
`FleetReportServiceTests.BeginnerVehicles_UsesPolicy_AndSkipsEquipment` проверяет, что в список попадает только подходящий транспорт.
`FleetReportServiceTests.BeginnerVehicles_DelegatesDecisionToInjectedPolicy` подменяет политику через Moq.
